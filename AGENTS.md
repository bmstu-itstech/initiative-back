# Инструкции для агентов

## Контекст и источники истины

- «Инициатива» — backend учёта активистов, отделов, направлений и руководителей Студенческого совета факультета ИУ МГТУ им. Баумана.
- Проект основан на `wemake-django-template`; сверяй соглашения шаблона с текущим кодом.
- Для автоматических тестов используй локальное приложение и тестовую БД.
- README описывает проект для людей; AGENTS задаёт инструкции агентам для всего репозитория.
- Источники истины: `pyproject.toml` — зависимости и настройки инструментов; `uv.lock` — разрешённые версии; `.python-version` — Python; `.github/workflows/initiative.yaml` — CI/CD.
- Стек: Python 3.13.13, Django 6, Django Modern REST (DMR), msgspec, PostgreSQL, Punq, Structlog, uv.

## Карта проекта и архитектура

- `server/apps/auth/` отвечает за JWT и роли; `server/apps/members/` — за активистов и структуру; `server/apps/events/` — за мероприятия и оргкомитеты.
- `controllers/` принимает HTTP-запросы, проверяет аутентификацию и роли, вызывает сценарии и формирует ответы. Маршруты объявляются в `controllers/urls.py`, подключаются в `server/urls.py`.
- `logic/value_objects.py` и `logic/export_rows.py` содержат DTO на `msgspec.Struct`; `logic/queries.py` — параметры запросов; `logic/exceptions.py` — прикладные исключения.
- `logic/usecases/` содержит вызываемые сценарии, зависящие от конкретных репозиториев и мапперов `infra`. Не меняй архитектуру попутно.
- `infra/repository.py` и специализированные репозитории выполняют ORM-запросы и обрабатывает ошибки БД; `infra/mappers.py` преобразует модели в DTO. Не переноси SQL и преобразование моделей в контроллеры.
- `models.py`, `managers.py`, `migrations/` описывают данные и схему; `admin.py` — администрирование. `members/views.py` является заготовкой.
- Зависимости регистрируются через Punq в `server/implemented.py`; контроллеры получают сценарии через `HasContainer.resolve()` из `server/common/di.py`.
- Настройки разделены на `server/settings/components/` и `environments/`. Вне пакета настроек обращайся к ним через `django.conf.settings`.
- Общие шаблоны находятся в `server/common/django/templates/`; тесты — в `tests/`. Каталог `docs/` пока пуст, хотя группа Sphinx-зависимостей сохранена.
- `.importlinter` частично отстаёт от реализации: не описывает `controllers`, а сценарии импортируют `infra`, и `members` использует роли из `auth`. Не выдавай эти контракты за выполненные.
- Проверяй ограничения импортов; сообщай расхождения отдельно, не ослабляя контракты ради проверки.

## Предметные правила и API

- Django `User` — учётная запись; `Member` — профиль активиста. Прямой связи нет; сохраняй разделение.
- Мероприятия — отдельное Django-приложение `server/apps/events/` со своими models, migrations, admin, controllers, logic и infra; тесты — `tests/test_apps/test_events/`. `EventOrganizer` связывает активиста `Member` со строковой ролью; уникальна тройка мероприятие–активист–роль, справочника ролей нет.
- API мероприятий — `/api/events/`, членства — `/api/members/{id}/events/`; корневой URL-конфиг подключает оба маршрута без импорта `events` из `members`. Списки без оргкомитета, карточка с краткими активистами. PUT заменяет оргкомитет атомарно; мягкое удаление сохраняет назначения. Общие мягкое удаление и renderer находятся в `server/common/django/`, схемы ответов и пагинация — в `server/common/`.
- Даты мероприятий содержат часовой пояс, начало не позже конца. Списки поддерживают пагинацию и сортировку по началу; общий список — нечёткий поиск названия. В CSV мероприятий места сериализуются JSON-массивом; CSV оргкомитета содержит ID активиста, ФИО, группу и роль.
- Карточка и CSV оргкомитета читают типизированные проекции через `values_list()`, не создавая ORM-модели для каждой роли. Преобразование в DTO остаётся в мапперах. PUT синхронизирует разницу назначений, сохраняя неизменившиеся; участников блокируют в порядке ID.
- `Direction` содержит отделы `Department`; `Member` связан с отделами через many-to-many. Один активист может состоять в нескольких отделах и иметь несколько назначений `Leader`.
- У `Leader` ссылки на отдел и направление необязательны. Ограничение принадлежности ровно одному подразделению удалено.
- Уникальность ФИО, Telegram, названий подразделений и должностей учитывает активные записи. Сохраняй соответствующие ограничения на уровне БД.
- Мягкое удаление задаётся `deleted_at`: `objects` выбирает активные записи, `all_objects` — все. `restore()` восстанавливает экземпляр; `is_deleted` является вычисляемым свойством.
- Не заменяй удаление экземпляра массовым `QuerySet.delete()`: переопределённый метод модели не обеспечивает автоматически мягкое удаление массовых или каскадных операций.
- Используй `MemberListOut` для списка, `MemberOut` для карточки, `Structure*Out` для структуры; сохраняй краткие ответы.
- Сохраняй поиск ФИО через `TrigramSimilarity`/`pg_trgm`, пагинацию `limit`/`offset`, фильтрацию и допустимые сортировки.
- CSV выгружается с разделителем `;` и UTF-8 BOM. При изменении экспорта согласовывай `MemberExportRow`, маппер, сценарий и HTTP-заголовки.
- Изменения API согласовывай между DTO, контроллерами, сценариями, мапперами, OpenAPI и тестами; сохраняй совместимость ответов.
- Предварительно загружай нужные связи через `select_related`/`prefetch_related`; учитывай сборку дерева структуры. Zeal в development выявляет N+1; не обходи его ради прохождения проверки.

## Окружение и запуск

- Работай из корня с Python из `.python-version`; управляй зависимостями через uv, не отдельными командами pip.
- Создавай `config/.env` из шаблона только при отсутствии. Замени заглушку ключа локальным секретом; существующие настройки не перезаписывай.
- Для локального запуска подними PostgreSQL через Compose; приложение вне Docker использует опубликованный порт и локальный `.env`.
- `DJANGO_ENV` по умолчанию равен `development`; production использует отдельные настройки. Необязательный `server/settings/environments/local.py` загружается последним и исключён из Git.

```bash
uv sync
docker compose up -d db
uv run python manage.py migrate
uv run python manage.py runserver
```

- Для полной Docker-разработки используй команды ниже; override автоматически подключает исходники и публикует порты 8000 и 5432.

```bash
docker compose up -d --build
docker compose exec web python manage.py migrate
docker compose exec web python manage.py createsuperuser
```

- `createsuperuser` выполняй при необходимости локального администратора; команды контейнера запускай через `docker compose exec web`.
- Локальная документация API: `/docs/swagger/`, `/docs/redoc/`, `/docs/stoplight/`, `/docs/scalar/`; схема — `/docs/openapi.json/`; состояние — `/health/`.
- `Dockerfile` находится в корне; скрипты запуска — в `docker/`. Production запускает WSGI через Gunicorn и использует внешнюю БД; Compose больше не задаёт Loki и сеть `observability`.
- Dockerfile не задаёт `USER`: по умолчанию процессы контейнера выполняются от root. Аргументы UID/GID в development override сохранились, но Dockerfile их больше не использует.
- Локальный Compose использует PostgreSQL 18, CI — PostgreSQL 15. Учитывай оба окружения при изменении запросов и миграций.
- Production-файл `docker-compose.ci.yaml` не содержит `build.context`; самостоятельная сборка им не проверена. Не исправляй deployment попутно.

## Стиль кода

- Новые и изменяемые комментарии пиши на русском. Массовый перевод унаследованных комментариев не требуется.
- Все новые и изменяемые docstring пиши на русском в формате Google Style Guide: краткое описание, затем необходимые разделы `Args`, `Returns`, `Raises` с английскими названиями.
- Не добавляй пустые разделы docstring; сохраняй технические имена и директивы инструментов.
- Соблюдай настройки Ruff: одинарные кавычки, длина строки 80, сортировка импортов и Google-конвенция docstring. Форматируй только относящиеся к задаче файлы.
- Соблюдай строгий Mypy с Django Stubs; не скрывай ошибки через `Any`, `cast`, `type: ignore`.
- Сохраняй соглашения `attrs`, `msgspec`, сценариев и DI; ограничивай изменения задачей.
- Не редактируй отчёты и кеши как исходники. Зависимости обновляй через uv вместе с lock-файлом.

## Тесты, проверки и покрытие

- **Порог покрытия неизменен: только 100%.** Сохраняй `--cov-fail-under=100` и измерение ветвей `--cov-branch`; учитываются `server` и `tests` по текущей конфигурации.
- Не снижай порог, не отключай coverage и не добавляй `omit`, `no cover` или другие исключения ради зелёной проверки. Достигай покрытия проверками поведения.
- Изменённое поведение проверяй тестами соответствующего слоя; исправления — воспроизводящим ошибку сценарием.
- `tests/test_server/` проверяет инфраструктуру; `test_auth/` — JWT и роли; `test_members/` разделён на API, сценарии, инфраструктуру, модели, миграции и администрирование.
- Используй фикстуры из `tests/test_apps/conftest.py`; тестовые настройки хеширования и media не переноси в production.
- Для Python/API/БД запускай целевые тесты, затем полный набор. Целевой запуск может не достигать общего порога; настройки не ослабляй.

| Проверка | Команда из корня |
| --- | --- |
| Ruff, как в CI | `uv run ruff check .` |
| Формат без изменений | `uv run ruff format --check .` |
| Типы, как в CI | `uv run mypy .` |
| Полный набор и покрытие, как в CI | `uv run pytest` |
| Целевые тесты | `uv run pytest tests/test_apps/test_members/test_infra/test_mappers.py` |
| Форматирование затронутого файла | `uv run ruff format <path>` |

- У Ruff включён `fix = true`; для проверки без автоматических правок добавляй `--no-fix`. Перед выполнением учитывай уже существующие пользовательские изменения.
- По характеру задачи дополнительно запускай `uv run flake8 .`, `uv run lint-imports`, `uv lock --check`, `uv run python manage.py check` и `uv run python manage.py makemigrations --check --dry-run`.
- Для миграций предусмотрены `uv run python manage.py lintmigrations` и `uv run python manage.py check_migrations --exclude-apps=axes`; проверяй их на локальном окружении.
- GitHub Actions запускает Ruff, Mypy и Pytest. Не утверждай, что остальные установленные инструменты автоматически выполняются CI.
- Schemathesis в `tests/test_apps/test_schema.py` сверяет API с OpenAPI через локальное WSGI-приложение. Обычный таймаут теста — 5 секунд; для проверки схемы настроено исключение.
- Для Markdown проверяй содержание, ссылки и diff. В отчёте различай выполненные, успешные и недоступные проверки.
- Сообщай измеренное покрытие только по полному запуску; настройки и старые отчёты не подтверждают 100%.

## Безопасность и миграции

- Не записывай пароли, токены, приватные ключи и значения production-конфигурации в код, документацию, коммиты, логи или ответы. Используй имена переменных и безопасные примеры.
- Сохраняй JWT-аутентификацию и проверки ролей. `Viewer` читает данные; `Editor` и `Admin` изменяют их; суперпользователь проходит проверку ролей. Группа `Admin` не заменяет `is_staff`.
- Не ослабляй Axes, CORS, CSP, HTTPS, проверки паролей и cookie ради локальной ошибки. Учитывай порядок загрузки настроек: `api.py` переопределяет CORS из `common.py`.
- Создавай новые миграции, сохраняй применённую историю, существующие данные, уникальность и возможность отката.
- Тестируй миграции через существующий `django-test-migrations`; изменение данных проверяй также на сохранность связей и коллизии. Не запускай миграции на production для локальной проверки.
- Используй транзакции для связанных изменений; преобразуй ошибки БД в прикладные исключения, не скрывая нарушения целостности.

## Коммиты, PR и завершение задачи

- Названия коммитов строго соответствуют Conventional Commits: `type(scope): описание`; scope необязателен. Допустимы `feat`, `fix`, `docs`, `refactor`, `test`, `chore`, `ci`, `build`, `perf`, `revert`.
- Примеры: `feat(members): добавить фильтрацию по группе`, `fix(auth): исправить обновление токена`, `docs: обновить инструкции для агентов`. Несовместимость обозначай `!` или footer `BREAKING CHANGE:`.
- Не создавай коммит без запроса и не изменяй чужую работу; проверяй `git status` и diff.
- В PR и отчёте описывай проблему, результат, проверки и ограничения. Не скрывай неуспешные команды.
- CI проверяет push в `main`/`dev` и pull request; push в `main` после успешных проверок запускает production-deployment и затем `docker system prune -f`. Не выполняй публикацию и очистку Docker как часть обычной локальной проверки.
